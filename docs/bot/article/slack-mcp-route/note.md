## 入口が増えたので、続きを見失わない形を考えた

私の環境では、ChatGPTからもClaude Codeからも、Slackを通してdotsに仕事を頼めるようになりました。ここでいうdotsは、Slackで話しかけられ、許可したGitHubの指示書を読み、別の実行環境で作業してbranchやPRを返すAIエージェントです。

接続できたこと自体も必要な一歩です。ただ、仕事をいくつか同時に進めると、その次の問題が出てきます。どの依頼の話をしているのか。最初に何を頼んだのか。いま何を待っていて、どこから再開すればよいのか。入口が二つになると、両方の会話を覚えているつもりでも、確かめる場所が散らばりやすくなります。

そこで私は、依頼ごとの番号、GitHubに置く指示書、進捗を書く看板、Slackの同じスレッドを組み合わせています。どちらのAIを使うかは、そのときの入口です。仕事の基準と現在地を同じ場所へ戻せるようにしました。

この記事は2026年10月4日時点の運用の整理です。dotsの一般的な提供条件や内部構成を説明するものではありません。接続手順は公式資料を確認し、試して分かったことは私の環境での観察として書き分けます。

## 短い番号が、長い説明の代わりになる

依頼の頭には「#番号 案件名」を付けます。番号は手元の台帳から取り、同じrepoと同じ案件keyなら同じ番号を使います。一度使った番号は再利用しません。GitHubのIssue番号やPR番号とは別にしています。

これは特別な仕掛けではありません。それでも、短い識別子を付けてからは、dotsとの続きの会話でもその番号で依頼を指せました。「さっきの件」だけで済ませずに、どの仕事かを先に揃えられます。repoやIssueを指定して状況を聞くことも、対象を絞る助けになりました。

ChatGPTで依頼を整理した後に、Claude Codeで進み具合を確認することもあります。そのとき、依頼を新しく作り直す必要はありません。同じ番号と同じSlackの会話、同じ指示書を渡します。入口を切り替えても、仕事の置き場所は引き継ぐ考え方です。

番号だけですべてが解決するわけではありません。番号が分かっても、要件の版や成果の版が違えば照合できません。そこで、もう一つ固定するものを用意しています。

## 指示は、いつの版かまで渡す

指示書は対象のGitHubリポジトリに置きます。README.mdには目的、触ってよい範囲、してはいけないこと、提出先、完了条件。REVIEW.mdには別の担当が確かめる観点。PROGRESS.mdにはいまの工程と次の一手を書きます。

依頼するときは、指示書のcommitを固定したURLを渡します。branchの最新版だけだと、最初に読んだ内容と後から見た内容が変わっているかもしれません。受け付けた側から「このcommitを読んだ」と返してもらえば、同じ版を見ているか確認できます。

進捗の看板は反対に、更新されることが役目です。対象repoに置いたPROGRESS.mdの最新版を追います。何を頼んだかと、いまどうなっているかを、別々に扱います。

指示には成果の形も書きます。「いい感じに進めて」では、どこで受け取れるのかが分かりません。この記事なら3媒体の原稿と5枚の画像が必要で、投稿は私が担当します。本文と画像ができたこと、検収が終わったこと、記事を公開したことは、それぞれ別に確かめる工程です。

要件が変わったら、その変更も同じ会話に残します。作業している相手が、いつの間にか違う条件で評価される状態にはしない。そのための固定した指示書だと考えています。

## Slackに送る文面は短くしている

Slackでは、案件の親メッセージを立て、その後の受付、質問、報告、修正を同じスレッドで続けます。送る文面には番号、対象repo、固定指示URL、看板URL、作業範囲、提出先を入れます。長い仕様の本体はGitHubへ置いてあるので、チャットに毎回コピーする必要はありません。

最初の受付では、番号の衝突がないか、指示のどの版を読んだか、その仕事に必要な環境を使えるかを返してもらいます。環境については、一般的にできるはずという説明で済ませず、依存の取得やブラウザなどを実際に試した結果が欲しいところです。

ここで私が分けているのは、次の三つです。

・送信したメッセージを読み戻せた
・dotsが同じ指示を読んで受け付けた
・作業を進め、必要なテストが通った

どれか一つの成功から、残りまで成功したとは判断しません。細かく感じるかもしれませんが、困ったときに戻る位置が分かります。

また、私の環境ではdotsの返答は依頼したスレッドに付きました。トップレベルの履歴だけを読むと、返信がないように見えることがあります。入口のAIに返信を確かめてもらうときも、スレッドの中まで読む必要があります。

## 二つの入口を用意する手順

接続は一度に大きな依頼で試さず、小さい送信から確かめます。以下は公式資料に沿った設定の要点です。プラン、組織のポリシー、画面の更新によって、使える機能や表示は変わり得ます。

### ChatGPT側

1. ChatGPTの設定でApps / PluginsからSlackを選びます。Install pluginが表示された場合は内容を確認して導入し、Connectから本人のSlackアカウントとワークスペースを認可します。これはChatGPTからSlackを使う設定で、Slack内の@ChatGPTを使う経路とは別です。
https://help.openai.com/en/articles/20001494-connecting-and-managing-app-accounts-in-chatgpt
https://help.openai.com/en/articles/20001536-chatgpt-with-slack-and-microsoft-teams

2. 組織で管理されている場合は、Slackと必要なアクションが有効かを確認します。Slack側の承認や、追加権限の再認可が必要になることもあります。
https://help.openai.com/en/articles/12525822-using-slack-in-chatgpt

3. 会話で必要なら「@」や「＋」からSlackを選び、自分宛てDMへ1通だけ送ります。リンクで本文と投稿者を確認して読み戻し、その後にdotsとのDMへ1通送り、返信スレッドまで読みます。最後の確認順序は、私が提案する試し方です。

### Claude Code側

1. Claude Code CLIを使える状態で、端末から claude plugin install slack を実行します。公式MCPサーバーへつなぐプラグインの導入手順です。対象Slackで連携を許可されていることが前提です。
https://docs.slack.dev/ai/slack-mcp-server/connect-to-claude/

2. Claude Codeで /mcp を開き、Slackを選びます。ブラウザで本人のアカウント、ワークスペース、権限を確かめてOAuth認証を進めます。私の環境では、認証後に新しいセッションを開くとツールが使えました。
https://code.claude.com/docs/en/mcp

3. 接続を確かめ、自分宛てDMへ1通送って読み戻します。続いてdotsとのDMへ1通送り、スレッドの返信を読みます。今回は追加の管理者承認を求められませんでしたが、必要な承認は環境によります。
https://slack.com/help/articles/202035138-Add-apps-to-your-Slack-workspace

## 止まっているように見えたら、外から確かめる

看板には工程、担当、状態、証跡、次の一手を書いてもらいます。「進行中」だけでは、待つのか、私が何かするのかを決めにくいからです。成果commitやCI、試したことと残った確認があれば、次に聞く内容を絞れます。

さらに、別の非公開repoに読み取り専用の監視を置いています。見るのはGitHub上のbranchの進み、PRとCI、対象ラベルのIssue、直近の取り込み時刻などです。看板は各repoに置いたまま、外から変化を見ます。

私の設定では既定60分、動きのないrepoを停滞として出します。この時間は運用上の目安で、AIの性能を測った数字ではありません。更新がない理由は外から分からないため、branch、PR、CIを先に見てから、同じ会話でdotsに尋ねます。

承認を待っているのか、依存を取得できないのか、環境の制限なのか、単に仕事が大きいのか。そこが分かれば、一工程だけを手元で補って戻すことができます。自動で同じ依頼を繰り返すより、重複を避けながら再開地点を揃えたいと考えています。

実際に、依存パッケージの取得を手元で補ったことがありました。大きいIssueでは2時間以上PRが出なかったこともあります。2026年10月2日から4日の観察から、いまは30〜60分を目安に区切れる大きさに分ける方針です。一般的な所要時間や、効果を測定した結果ではありません。

## 受け取る作業まで、依頼に含めておく

成果が出たら、そのSHAを基準に独立レビューをします。作った担当とは別の担当が指示と成果を照合し、私も手元で必要な確認をします。Windows実機や画面、本番に関わる確認は、別環境のテスト成功から推測しません。

merge、本番反映、releaseも、依頼に含めない限り自動で進めません。この記事の公開も私の担当です。原稿を提出した段階で「3媒体に公開できた」とは書かず、投稿と実URLでの画像表示まで、それぞれ状態を残します。

まだ手元で確かめる作業はあります。監視から停滞の原因を自動で知れるわけでもありません。それでも、依頼の基準、現在地、受け取る条件を揃えておけば、途中で入口を変えても、やり直す工程を小さくできます。

同じ形を試すなら、まず小さい一件で、送信から検収まで一周するところからでよいと思います。どの情報が足りなかったかを、その後の指示書に戻していく。その繰り返しとして、この仕組みを使っています。

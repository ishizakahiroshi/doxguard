# 業務処理を守る例外記録の設計記事

依頼番号: #20261005-003

## 目的

業務アプリケーションで捕捉した異常を不具合台帳へつなぎながら、記録処理の失敗を元の業務へ波及させない設計を、匿名化した技術記事として説明する。

媒体はQiita。制作担当はdots。今回の承認範囲は本文・全図版・告知文の下書き制作と提出まで。媒体投稿、サイト公開、X送信、mergeは実施しない。依頼資料のGitHub公開と記事の媒体公開を区別する。

このrepoは制作指示の受け渡し先であり、題材のシステムではない。repoの製品紹介や元案件の探索は不要。読める材料はこのディレクトリの文書だけとし、元の案件・顧客・システムを推測しない。

## 実施内容

1. FACTS.mdとBRIEF.mdを読み、本文と図版を制作する。
2. 本文・hero・infographic・本文挿絵・figを担当する。固定猫だけは手元検収で重ねる。
3. 独立した担当がREVIEW.mdで事実・機密・画像・日本語を確認する。
4. この依頼のディレクトリだけを変更した作業branchとPRを提出する。Git操作は一担当が所有する。

提出物はdraft.md、完成PNG、x-post.md、src/の元データ・生成指示・検査記録、更新したPROGRESS.mdとpublication.json。元データや没画像は直下に置かない。

受付返信に番号、読んだ固定指示commit、作業branch、画像生成・文字合成・PNG化・画像目視の実行可否を記載する。未確認の能力を不能と断定せず、各工程で実際に試す。追加課金・認証情報の配置は行わない。

完成画像の実物確認と手元による独立検収は、dotsの自己報告と別の段階。制作不能な工程があれば失敗分類と再開条件を記録する。同じ失敗を根拠なく繰り返さない。

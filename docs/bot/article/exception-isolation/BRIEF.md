# 制作条件

## 確定した設定

媒体: Qiita。設計判断の記事。分量は約4000字。題材はFACTS.mdの一般化済み事実。検索語は例外処理、エラーログ、不具合台帳、業務ロジック。タイトルは1案を自分で選ぶ。業務由来として厳格に匿名化する。分類はworks。タグは例外処理・ログ・設計・テストなど適切な3〜5個。音声投稿はしない。

画像は約4000字なら全4枚: hero 1、絵と文字のinfographic 1、AI生成の本文挿絵1、正確な概念図fig 1。本文確定後に字数と画像密度を確認する。全体をクリアな寒色パレットで統一する。別の冒頭要約は置かず、導入から要点へ入る。

## 文体と構成

ですます調。読みやすい短い段落と会話的な見出し。実践できる設計上の確認点を早めに示す。タイトル例は「例外ログを増やすときに業務処理を壊さないための設計」。タイトルは調整可能。

構成の候補: 捕捉しただけでは台帳に届かない → 記録を業務トランザクションから離す → ログ失敗が戻り値や認証へ与える副作用 → 機密を保存しない許可リスト → 通常の失敗と不具合の分類 → 静的・合成・配信・実操作の証拠を分ける → 保証できない境界と運用。

固有の実装手順や配信構成は載せない。一般的な擬似コードを添える場合も、二次障害を抑える意図とその限界を説明する。throw、return、transactionの順序を変えないことを具体的に述べる。元の業務失敗自体を握りつぶす書き方にしない。万能な監視システムの宣伝にしない。

他の公開記事を関連リンクにする場合は実URLと内容を実際に確認する。私有資料・draftへリンクしない。適切な公開記事が確認できなければ無理に置かず、その結果を検査記録に残す。技術仕様を外部資料から追加する場合は公式文書で検証し、リンクを付ける。

手元の記事台帳と公開記事索引を照合し、公開ページも確認した関連記事は「UIフリーズを追うログは、リリース前にパージできる形で仕込む」 https://zenn.dev/ishizakahiroshi/articles/20260927-ui-freeze-instrumentation-purge 。本文の締め近くに関連リンクとして1回だけ置いてよい。ログの副作用・入力本文を収集しない方針・確認範囲を分ける考え方が関連する。この公開記事の固有実装を今回の業務システムへ転用したと主張しない。

## 画像

heroは無料のWeb画像生成を優先する。有料APIや追加課金へ切り替えない。本文の絵はChatGPT Web、Gemini Web、利用可能な画像生成toolの順に実行可否を確認し、採用元を記事内で統一する。画像生成へ渡す文章もこの匿名化済み資料だけから作る。

heroは猫を描かず重ねず、1600x900の右下に幅340×高さ250pxの空間を確保し、タイトルと被らせない。固定猫は手元の検収で重ねる。猫素材を探したり取得したりしない。

hero背景の生成時には日本語を描かせない。タイトルはHTML等で後から合成し、完成heroも1600x900にする。

infographicは文字のないAIイラストにHTMLで日本語を合成し1600x900のPNGへする。絵の生成が失敗した場合のみHTML組版に落とし、変更理由を記録する。figは「業務経路と記録経路」「保留保存と台帳確定」を示す一般的な概念図とする。実構成・台数・ブランド・ロゴ・生ログ・実画面を描かない。figと挿絵の直後に画像がなくても意味が通る説明を1〜2文添える。

完成PNGを実際に目視し、日本語の欠け・余分な文字・ロゴ・機密・図と本文の矛盾を確認する。存在だけでは検収済みとしない。目視できなければ未実施と記載する。生成指示、元HTML/SVG、中間画像はsrc/に保存する。

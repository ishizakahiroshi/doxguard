# 公開可能な事実と主張の境界

この資料は業務由来の対応を一般化したもの。元の記録、ソース、顧客情報は提供しない。出典を調査して元のシステムを同定してはならない。

## 記録から確認した内容

- 例外を捕捉して終了や復旧を行う経路に、不具合台帳へ接続されていない箇所があった。画面・サーバー・定期処理の経路を調査し、対象の異常記録を追加した。
- 記録処理を業務処理から分離した。捕捉時は保留領域へ保存し、別の回収処理が専用のトランザクションで台帳へ反映する。反映の確定後に保留データを取り除く。
- 元の戻り値、例外の再送出、応答、業務トランザクション、再試行、後片付けが変わらないかを確認した。
- 画面からの自動報告が、通常の認証セッションや最終操作時刻の更新に影響しないよう経路を分離した。長い保存処理へ入る前にセッションのロックを解放する。
- 自動記録は収集可能項目を許可リストで限定する。例外の生メッセージ、SQL、入力本文、Cookie、引数は保存しない。調査に必要な分類や発生箇所、関連づけ用の識別情報だけを扱う。
- 想定された入力不備、権限拒否、通常の業務上の競合、利用者による取消を一律に不具合扱いしない。記録対象と除外理由を整理した。
- 例外を投げない失敗や処理の未完了も対象を検討した。catchの追加だけでは網羅したことにならない。
- 重複抑制、容量上限、回収量の上限、保持と停止方法を設計した。
- 静的検査、合成データ・代替依存を用いた失敗注入、CIで確認した。ソースの配信後には対象環境のファイル一致を確認し、現行仕様へ反映した。

## 必ず記載する未確認事項と限界

- 実画面の操作から実台帳への到達までの通し確認は実施していない。ブラウザ確認、スモークテスト、検証用の実データ投入は今回の確認範囲外。
- 配信ファイルの一致は実際の業務動作成功や台帳到達の証明ではない。
- 保留保存は台帳登録完了ではない。容量超過、回収処理の停止、認証期限切れ、強制終了などで記録できない境界がある。
- すべての異常が必ず記録される、影響が完全にゼロ、無条件のexactly-onceという保証はできない。
- ログアウト時に常にローカル保存が消えるとは断定しない。異常終了や保存領域の失敗を考慮する。
- 元の詳細構成を再現するコードは出さない。コードを載せる場合は説明用に新しく作った擬似コードと明記し、実行・検証済みと扱わない。

## 出してはいけない情報

会社名、案件名、製品名、人物名、部署、業種、元repo、実URL、ホスト、実パス、関数名、テーブル名、画面名、環境の数と配置、実日付、実件数、実ID、commit、ログの原文、秘密値。伏字・イニシャル・先頭だけのマスクも不可。一般名と概念図へ置換する。

個人の感情、会話、所要時間、顧客の反応、影響規模を創作しない。公表済みの著者プロフィールを除き、人物情報は加えない。

# 記事と画像の既定
## 本文
日本語。本人の開発の仕方の紹介と、やって分かったことの整理。本人の未経験の出来事や感情を創作しない。
仮題は「dotsに作り直し途中のDesklyの機能を任せてみた: 取り決め、1回の承認、別のAIのレビュー」。タイトル案と構成はdotsが比較して自分で決めてよい。
主題は開発の仕方。読んだ人が自分のAIエージェントに複数工程を任せるときの型(取り決めを先に書く/最初に1回だけ承認/止まる条件/検証はCI/取り込む前に別の製品のAIが全行を読む)を持ち帰れることを目標にする。作った機能の仕様説明を主題にしない。
前作の続編として、冒頭近くで前作を1文で紹介しリンクする(FACTS.mdの3媒体URLのうち、その媒体のURL)。前作を読んでいなくても分かるように、前作の仕組みは2〜3文で補う。
Zennは型と手順を詳しく(type: idea でも tech でもよい)。:::message で止まる条件などをまとめてよい。
Qiitaも型と手順を詳しく。指示書に書いた項目(止まる条件、検証の書き方、印)とレビューで見つけたテストの弱さの型を具体的に。
noteは、なぜこの進め方にしたか、途中で何が起きたか、まだ足りないことを読みやすく。手順は要点に絞り、詳しくはZennかQiitaへ誘導してよい。
分量の目安は各5000字前後。水増ししない。大げさな成功宣言、広告口調、架空の会話、長いダッシュ表現を避ける。
3媒体とも冒頭に「この記事自体もdotsが執筆しています」を明記する。合わせて事実整理・独立検収・公開が手元担当であることを開示する。
「別のAI」は手元のClaude(Anthropic)、dotsはOpenAIの常時稼働エージェントであることは書いてよい。どちらが優れているという比較にしない。違う製品なので見落としが重なりにくい、という範囲に留める。
外部の数値や仕様(GitHubの規約など)は出典URLを近くに置く。URLを置けないものは書かない。
Zennは有効なfrontmatter(title, emoji, type, topics 最大5, published:false)付き。
Qiitaは有効なfrontmatter(title, tags, private:false, updated_at:'', id:'', organization_url_name:null, slide:false, ignorePublish:false)付き。タグは内容に沿う既存タグを最大5つ。
noteはタイトルをH1、見出しを##/###、箇条書きに「・」を使い、URLの直後に文字を続けない。推奨タグは本文と別に書く。

## 記事末尾のフッター
本文の締め、区切り線 --- 、フッターの順。装飾なし。ZennとQiitaは同じ文面。noteは先頭に図解版の案内2行を足す。
AI生成画像の開示は、使った画像の実績に合わせて切り替える。hero(生成シーン)と、絵と文字を合成したinfographicと挿絵を使う場合の文面は次のとおり。

```
---

※ ヘッダー画像とインフォグラフィックの絵は AI（画像生成）で作成しています。

※ 本文の挿絵も AI（画像生成）で作成しています。

書いた人: ishizakahiroshi
群馬の北部で、保護猫2匹と暮らす、在宅エンジニア（何でも屋）
https://ishizakahiroshi.com/
https://github.com/ishizakahiroshi
X（業務委託・各種相談はこちら）：
https://x.com/ishizakahiroshi

バックエンド・インフラ・AI連携まわりで、業務委託のご相談を受け付けています。フルリモートです。スポットや週2〜3時間からでも歓迎で、いろんな案件に携われたらうれしいです。こんな相談、歓迎です。
```

noteだけ、上の区切り線の直後に次の2行と空行を入れる。

```
※ 各記事の図解版（画像と図と関連リンクをまとめたページ）は、個人サイトの記事一覧から辿れます。
https://ishizakahiroshi.com/#articles
```

前作へのリンクは冒頭近くと、フッターより前の本文の締め近くの2か所に置く。

## note の画像差し込み目印
note.md では、画像の位置を次の5行で示す(Nは登場順、内容とファイル名を入れる)。Zenn・Qiitaでは通常の画像記法にし、区切り線を残さない。

```
===========================================================================================
===========================================================================================
【画像N｜<画像の内容>｜<ファイル名.png>｜ここに差し込み、この行は削除】
===========================================================================================
===========================================================================================
```

## 画像
約5000字で5枚。hero1、全体要約infographic1、文字なし挿絵1、fig2の全役割を制作する。
3媒体で同じ図版を共有し、全5枚を適切な位置に挿入する。01から記事登場順に連番を付け、ファイル名は 0N-dots-dev-flow-<役割>.png とする。
heroとinfographicを冒頭に置き、その後本文に挿絵と図。完成PNGをこのディレクトリ直下に置く。
1600x900を基本、スマホでも読める余白と文字サイズ、日本語の欠字・はみ出しを等倍目視する。Zennへ置く画像は1枚3MB以下にする。
1記事1パレット。前作と見分けがつく基調色にする。
hero: AIで文字も猫もないシーンを生成し、日本語タイトルと固定猫PNGを後から合成する。HTMLだけでheroを作らない。
固定猫はassets/mascot_cats.pngの実素材をそのまま使い、再生成しない。右下に合成し、タイトルと競合させない。
infographic: 絵と文字の組み合わせ。絵は文字なしで生成し、日本語は編集可能な組版で合成する。heroの直下、最初のH2前。内容は4手順(取り決め→1回の承認で連鎖→別のAIのレビュー→直して読み直して取り込み)と、それぞれで起きたこと1行。
挿絵: 文字、数字、ロゴなしで、作業役が工程を進め、最後に別の目が全体を読み直す場面や比喩を伝える絵。
fig1: 連鎖の流れ。最初の1回の承認→工程0(Draft PR)→工程1〜4(各工程でPRのCI)→止まる条件に当たれば止まって人へ→最後に別の製品のAIが全行を読む→人の受入と取り込み。人が関わる点が2か所(最初と最後)と止まったときだけ、と読める図にする。
fig2: レビューで見つかったものの内訳と、テストの弱さの3つの型(期待するエラーの種類を見ない拒否/直列で処理される「同時100件」/呼ばれない関数の回数0)。数字はFACTS.mdの範囲だけ。
図に固定猫を入れない。一般的な飾り箱でなく因果・順序・担当が読める図にする。
既存契約内の画像生成を試す。追加有料APIは禁止。利用不可、生成、文字合成、素材合成、PNG化を別工程で記録する。
sourceと最終PNGのhash、生成経路、画像目視結果、altをsrcに残す。

# 既定で確定した制作条件

1. 媒体: note。
2. 作業の種類: 書き換え。SOURCE.md の事実と論点を落とさず、依頼者の文体ルールへ直す。
3. hero: 画像生成を試す。追加課金なし。猫なしの 1600x900 PNG。
4. infographic: 1枚。絵は文字なしで生成、文字は HTML で合成。絵の取得に失敗した場合は HTML 組版（文字だけ）に切り替え、理由を記録。
5. 色: クリア寒色。ネイビー、淡い青、白、アクセントは琥珀色で、全画像を統一。
6. 記事タイプ: 論考（エッセイ寄り）。
7. 分量: 既定は論考で約6,000字だが、SOURCE.md が約20,500字で17項目あり、既定では事実を落とすことになる。そのため**事実と論点を落とさないことを優先**し、約9,000字を目安、10,000字を超えない範囲にする。短文の列挙と重複の説明を畳むことで縮める。字数のために項目を削らない。
8. 画像の枚数: 計8枚。hero 1、infographic 1、本文挿絵 3、fig 3。分量から決めた枚数で、役割は下の「画像」に書く。
9. 題材: SOURCE.md と FACTS.md だけ。調査で足すのは一次情報の確認であり、新しい論点や事案を足さない。
10. 検索語: 情報漏えい、不正アクセス、国内インシデント、一次情報、ハッシュ化。導入の200字以内に自然に入れる。
11. 冒頭の別 TL;DR: なし。infographic で要約する。
12. 機密: 個人。各社の公表は公開情報。私有情報・実パス・認証情報なし。
13. タイトル: 1案。SOURCE.md の題を元に、体言止めや煽りを避けて整える。句点を含む長い題は短くしてよい。
14. 題材分類: misc。製品の宣伝ブロックは不要。
15. タグ: note 用に13個を本文の最終行へ（下の「note の体裁」）。
16. 今回の公開範囲: 制作と Draft PR 提出まで。note・サイト・SNS への投稿は行わない。
17. 音声: なし。
18. 制作担当: dots。固定猫を重ねる工程と最終独立検収だけ手元。

## 書き換えの方針（最重要）

事実は SOURCE.md と FACTS.md のとおり。直すのは「書き方」。依頼者の言い回しや感想は、意味を変えずに残す（「めんどくさい」「無理ゲー感」など）。新しい感想や体験を足さない。

SOURCE.md の癖と、直し方:

・一文ごとに改行する短文の列挙（「氏名。住所。電話番号。」「認証。メール。教材。…」）が多い。2〜3文の段落にまとめるか、項目が本当に並列のときだけ箇条書き（note は「・」）にする。
・体言止めと対句の連続、同じ語尾「〜です。」の反復を崩す。文の長さを不揃いにし、短い言い切りを時々挟む。
・太字（`**`）が多い。note へ貼ると邪魔なので、記事全体で 3 か所以内に絞る。
・章見出しが `# `（H1）になっている。note の本文は大見出し `## `、小見出し `### `。H1 はタイトルだけで、本文には残さない。
・「公式発表：」と URL を並べた一覧が冒頭にもある。冒頭は社名を文章で挙げるだけにして URL は付けず、各社の節の初出で 1 回だけ URL を置く。末尾の「確認した主な一次情報」の一覧は残してよい（出典一覧として）。
・「〜することが大切です」「重要なのは」「ポイントは」「〜と言えるでしょう」の総括定型を新しく足さない。
・三段構成のテンプレ（まず・次に・最後に）にしない。

## 文体と構成

敬体。一人称の「私」「僕」は避け、「考えた」「思った」「気づいた」などの動詞で主体を出す。必要なら「自分」。導入は短く 1〜2 文で、具体から入る。段落は 1〜3 文を基本に、意味のブロックごとに改行。H2 は会話的な問いかけ・語りかけにする（良い例「3000 件あるはずの画面が、13 件しか出ない」。避ける例「原因分析」「調査結果」）。トーンは柔らかく、上から教えない。「〜だと思っています」「〜かもしれない」の留保を残す。

**ダッシュ（`—` `―` `——`）は本文・見出し・図のラベルすべてで使わない。** 画像 HTML 内のテキストにも適用。代わりに句点で切る、読点でつなぐ、「。その」「。だから」で受け直す。

SOURCE.md の流れは大きく変えない。きっかけ、「この1週間」の意味の注意書き、各社の公表（日付順）、共通して見えるもの、「全部ハッシュ化すればいいのか」への答え（ハッシュ・暗号化・鍵・検索・ログ・コピー・退会者・本人確認書類）、漏れる前提の設計、攻撃者から見た価値、今後見ておきたいこと、公表が増えたのか見えるようになったのか、担当者のしんどさ、エンジニアとしての見方の変化、結論を出さない、の順。章の見出しや並びは、読みやすさのために前後させてよいが、論点は落とさない。

導入で、依頼者の以前の 2 本の記事（FACTS.md の関連記事）に触れる。URL は初出 1 回ずつ、段落の直後に置く。専用の「前回の記事」ブロックは作らない。`## おわりに` の前に `## あわせて読みたい` を置き、FACTS.md の「あわせて読みたいの候補」を 1 本、どう今回とつながるかの 1 行を添えて載せる（理由をダッシュでつながない）。

他の記事・公式資料・各社の発表へ言及した段落は、直後に原典 URL を置く。「あの記事で読んだ」「公式発表で見た」だけの言及は禁止。URL が見つからなければ言及を落とすか「（出典未確認）」と書く。

締めは大きな主張で終わらせない。SOURCE.md の最後の「データを守る一番簡単な方法は、そのデータを持たないこと」とその但し書きを、小さな決意か、言い切らない終わり方で受ける。この記事は 2026-10-06 時点のスナップショットで、数字が動いたら追記する、という趣旨は残す。

## note の体裁

draft.md の構造は note 形式。

・H1 がタイトル（note のタイトル欄に入れる）。本文の章見出しは `## `、小見出しは `### `。
・箇条書きは `・`（中黒）。`- ` は使わない。
・画像の位置は単独 1 行にしない。画像ごとに、長い `=` の区切り線を前後 2 本ずつ置いた 5 行の目印ブロックにする。本文図（fig）と hero・infographic は `【画像N｜<内容>｜<ファイル名.png>｜ここに差し込み、この行は削除】`、AI 生成の本文挿絵は `【挿絵N｜<内容>｜<ファイル名.png>｜ここに差し込み、この行は削除】`。
・図と挿絵は目印ブロックの直後に、画像が無くても意味が伝わる 1〜2 文の地の文を置く。
・hero は冒頭、infographic は導入の後かつ最初の H2 の前。
・URL の直後に説明文やカッコを続けない（note でリンクが壊れる）。説明は URL の前か別の行に。
・装飾（太字の多用、絵文字、見出し化）をしない。

記事末尾は、本文の締め、`---`、次のフッター、空行、ハッシュタグ 13 個の 1 行、の順で固定。フッターの文面は次のとおり変えない。

```text
---

※ 各記事の図解版（画像と図と関連リンクをまとめたページ）は、個人サイトの記事一覧から辿れます。
https://ishizakahiroshi.com/#articles

※ ヘッダー画像とインフォグラフィックの絵は AI（画像生成）で作成しています。

※ 本文の挿絵も AI（画像生成）で作成しています。

書いた人: ishizakahiroshi
群馬の北部で、保護猫2匹と暮らす、在宅エンジニア（何でも屋）
https://ishizakahiroshi.com/
https://github.com/ishizakahiroshi
X（業務委託・各種相談はこちら）：
https://x.com/ishizakahiroshi

バックエンド・インフラ・AI連携まわりで、業務委託のご相談を受け付けています。フルリモートです。スポットや週2〜3時間からでも歓迎で、いろんな案件に携われたらうれしいです。こんな相談、歓迎です。

#タグ1 #タグ2 … #タグ13
```

ハッシュタグは `#` 付き・半角スペース区切りの 1 行で、ラベルや説明を付けない。基本 10 個と旬の 3 個。SOURCE.md 末尾のタグ案を土台にしてよい。#ランサムウェアは、記事内で引用した公式ページが実際にその語を使っている場合だけ入れる。infographic が HTML 組版（文字だけ）に落ちた場合は、フッターの 2 行目を「※ ヘッダー画像は AI（画像生成）で作成しています。」に変える。

## 画像

完成 PNG は記事に現れる順に `NN_` を付ける（01_hero.png、02_infographic.png、03_…）。1600x900 を基本とし、素材・HTML・SVG・生成プロンプト・没版は src/ へ。draft.md から参照する完成 PNG だけを案件フォルダ直下に置く。

hero は、猫を描かず重ねず、右下の幅340×高さ250px を空けてタイトルと被らせない。固定猫素材は要求しない。絵柄は、次々に届く発表の通知に囲まれた、静かな机や窓辺のような場面。タイトルは短い日本語（候補「この1週間、漏えい多すぎないか」）。実在の企業ロゴ・実在人物の顔・実在サービスの画面を入れない。

infographic は絵と文字の組み合わせ。各列の絵は文字なしで生成し、文字は HTML で重ねる。3 列「公表が続いた（各社の単位はバラバラ）→ 漏れた後に何が読めたか（持たない・分ける・消す）→ 今後見ておきたいもの（原因・侵入期間・二次被害・保持期間）」。合計被害人数は書かない。

本文挿絵 3 枚（場面・感情・比喩）。1 つ目は導入の、発表が次々に出て読む手が追いつかない場面。2 つ目は「持たない」「分ける」の比喩（倉庫・鍵・別の金庫など）で、「一番強いのは存在しない」の節。3 つ目はセキュリティ担当者のしんどさの節。文字を入れず、実在のロゴ・人物を入れない。

fig 3 枚（正確な情報を伴う図。HTML で組んで PNG 化）。1 つ目は件数の単位の整理で、数値を公表した各社の件数と単位（アカウント・人・件・登録ユーザー数）を並べ「単位が違うので足さない」と示す。数値は FACTS.md のものだけ。2 つ目は「ハッシュ化／暗号化＋鍵を分ける／検索用の HMAC／持たない・消す」の使い分けで、「元に戻す必要があるか」を軸にした図。3 つ目は「別サーバー・別インフラ・保存しない」の整理で、各社が公表で挙げた分離（イープラス、The Japan Times、大起水産、ムーンスター、アバハウス、焼肉きんぐ）を、公表された言葉のとおりに並べる。

本文の数値を直したら、図・infographic・要約も同期する。画像内の文字も本文と同じ禁止ダッシュのルール。

画像生成、文字合成、PNG 化、目視を別の工程として記録する。可能なら画像生成を並列にし、最初に採用した生成元で絵を統一する。未試行で制作不能としない。日本語の文字化け、切れ、画像抜け、余白、1600x900、横あふれ、画像リンクの存在を確認する。色は 1 記事 1 パレット。

## 最初に：これは「この1週間に発生した事件一覧」ではありません

最初に大事なことを書いておきます。

この記事でいう「この1週間」は、主に**2026年9月29日から10月5日に企業や組織が公表・更新した情報**を指しています。

攻撃そのものが、この期間に行われたとは限りません。

たとえば、

- 9月に攻撃され、10月に発表されたもの
- 以前から調査していて、この期間に対象件数が確定したもの
- 利用者からの問い合わせで発覚したもの
- システム障害として始まり、後からサイバー攻撃の可能性が報道されたもの

などが混ざっています。

また、「660万件」「57万人」「1078万件」など数字の単位もバラバラです。

人なのか。

会員なのか。

アカウントなのか。

レコードなのか。

問い合わせ履歴なのか。

同じ人が複数件含まれているのか。

ここを無視して足し算すると、ものすごい数字は作れます。

ただ、それは正確ではありません。

なので今回は、「合計○千万人漏えいした」という見せ方はなるべくしません。

それぞれの会社がどういう単位で何件と発表しているか、そのまま見ていきます。

本人確認書類は別管理。

検索用データは必要ならHMAC。

権限は最小化。

古いデータは消す。

不要なログは残さない。

本番データを開発環境へコピーしない。

DBを用途ごとに分ける。

委託先へ渡す項目を減らす。

バックアップも暗号化。

そして、侵入されたらすぐ止められるようにする。

一つ一つは地味です。

でも今回の各社発表に何度も出てきた、

「カード番号は保持していない」

「パスワードは別サーバー」

「購読者DBは別インフラ」

という説明を見ると、

こういう地味な設計が実際に被害範囲を決めるのだと思います。

# 逆に「全部暗号化してあるので安心です」も怖い

暗号化という言葉は安心感があります。

でも、

どの暗号方式か。

鍵はどこにあるか。

誰が復号できるのか。

API経由なら復号できるのか。

管理者権限を取られたらどうなるのか。

バックアップは？

ログは？

検索インデックスは？

CSVは？

という話があります。

たとえば攻撃者がアプリケーションサーバーまで完全に乗っ取った場合。

正常なアプリと同じ権限でKMSを呼べるなら、アプリが復号できる情報は攻撃者も復号できる可能性があります。

暗号化は強い。

でも万能ではありません。

だから、

暗号化。

権限制御。

ネットワーク分離。

監視。

レート制限。

大量取得検知。

異常行動検知。

などを重ねます。

結局また面倒になります。

# 一番強いのは「存在しない」

結局、一番強いセキュリティ対策は何か。

自分は今回の記事を調べていて、

**そのデータを持っていないこと**

だと思うようになりました。

カード番号を持っていなければカード番号は漏れない。

CVVを保存していなければCVVは漏れない。

古い本人確認画像を削除していれば昔の画像は漏れない。

開発環境に本番データをコピーしていなければ開発環境から本番個人情報は漏れない。

ログへパスワードを書いていなければログからパスワードは漏れない。

当たり前です。

でも、

「あとで使うかもしれない」

「分析に便利」

「問い合わせが来たとき必要」

「消す処理を作るのが面倒」

で、データはどんどん残ります。

ストレージが安くなったこともあります。

技術的に保存できることと、

保存すべきことは別です。

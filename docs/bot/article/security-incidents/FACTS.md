# 事実の台帳と書いてはいけない主張

情報源は依頼者の原稿 SOURCE.md（2026-10-06 時点）。各社の発表は SOURCE.md に書かれた内容であり、dots がページで再確認するまでは「原稿記載」。再確認できた項目は SOURCES.md に、ページの題名・公表日・本文の該当箇所と合わせて書く。

**URL の確度の区分**

・具体: 発表そのもののページを指す URL。本文の数値・項目をこの URL で照合する
・上位: サイトの入口や一覧を指す URL（発表の個別ページではない可能性がある）。本文の数値・項目を照合できない場合は、記述を原稿のまま残して「出典の個別ページ未確認」と SOURCES.md に書く。個別ページが見つかれば URL を差し替える

## 依頼者自身の記述（事実と分けて扱う）

・X に書いた依頼者の投稿（原稿の引用ブロック）。そのまま引用する。投稿の URL は原稿に無い。創作せず、「Xに書いた」と本人の投稿であることを本文で分かるようにする
・「めんどくさい」「無理ゲー感」などの感想、設計への見方（持たない設計が強い、別サーバーや分離が範囲を決める、など）は依頼者の意見。事実の文と混ぜず、意見だと分かる書き方にする
・暗号化、ハッシュ化、HMAC による検索用の列、鍵管理、データ保持期間などの説明は一般的な技術の話。原稿の説明の範囲で書き、反復回数やパラメータなどの数値、実在の実装コード、未確認の仕様を足さない。例の列名（email_ciphertext, email_lookup_hash）は合成の例

## 書いてはいけない主張

・各社の事案の原因を断定する。「この脆弱性が原因」「この会社の対策が悪かった」
・NetScaler の脆弱性と各社の事案を結びつける。原因は AI による攻撃の自動化、日本企業のセキュリティが低い、と一言で片付ける
・各社の件数を足して合計の被害人数を作る
・原稿にない漏えい項目・件数・原因・日付を、一般論から補う（佐川急便、ヤマト運輸、第一生命、日本経済新聞社、大和証券）
・大阪公立大学の障害をサイバー攻撃と断定する
・「情報漏えいの心配はいりません」のような安心の言い切り
・原稿にない依頼者の体験、作業時間、その場の様子の創作
・この記事は 2026-10-06 時点のスナップショットである。この日付より後の動きを書かない

## 匿名化と秘匿

各社の公表は公開情報なので社名・事案名は書いてよい。私有 repo 名・実ファイル名・ホスト名・実パス・ユーザー名・顧客情報・私有会話 URL・認証情報は書かない。画像に実在の企業ロゴ、実在人物の顔、実在サービスの画面を入れない。
